Overall verdict

Step 8 is functional, well-cited, and green — the validators work, errors carry BR references, and the suite passes cleanly. But measured against the project's own standard (naive, absolutely explicit, behavior-tested oracle) it falls short in three structural ways:

  • One invented rule exists in code with no basis in the business rules or GAN spec (“Marshal must be placed on an empty square”, C1) — plus its duplicate in the older GAN validator.
  • Two public validation stacks now coexist and provably disagree on the same action+state (C2) — the opposite of a single naive oracle.
  • Two tests validate the current code instead of behavior: one fixture is an illegal game state (A1), one assertion locks in behavior that contradicts BR-TURN-002 (A2).

All findings below were confirmed empirically (see Verification).

Axis 1 — Test quality: do the tests test behavior, or only validate the current code?

Mostly behavior — fixtures are built through the real GSFEN parser and assertions target legality outcomes with BR attribution. The Self-Check test saved from Step 7 is exemplary. But two tests actively validate the code-as-written rather than the rules, and some behavioral coverage is missing.

A1High Illegal-state fixture makes an acceptance test validate the unreachable

oracle/tests/game/deploy.test.ts:99–106 — “accepts placement on friendly stack under size 3 (BR-DEPLOY-005)”

The fixture encodes the stack 4,MP,4 — Marshal at the bottom, Pawn on top. GSFEN stacks read bottom→top, so this position violates BR-STACK-004 (“Marshal is always the topmost piece”); validateState rejects it with V3 (PROBE-1). It slips through because parseGSFEN deliberately skips semantic validation, and the test helper never calls validateState.

The damage: with the legal encoding of a friendly size-2 stack containing a Marshal (PM — Pawn bottom, Marshal top), the same placement must be rejected (cannot stack on a Marshal). So the asserted acceptance only holds for an impossible position; if someone “fixes” the fixture to a reachable state, the test fails. It validates what the code does, not what the rules say.

Fix: use a non-Marshal stack (e.g. SP) for this test, and consider running validateState inside the gsfenState() test helper so illegal fixtures fail loudly at setup.

A2High A test locks in behavior that contradicts BR-TURN-002

oracle/tests/game/battle.test.ts:439–440 — “Active player should NOT be flipped (that's Step 10)”

The test asserts afterState.turn.activePlayer === 'white' after a Play. BR-TURN-002 requires the Active Player to pass to the Opponent after a Play. This codifies the incomplete Step-8 applyMove as expected behavior: when Step 10 implements the flip, this test must be rewritten, and until then it would fail the correct behavior. It is the clearest instance in this commit of “test validates current code, not behavior.”

Fix: delete the assertion, or convert to it.todo/it.fails with a BR-TURN-002 reference so the suite documents the gap instead of cementing it.

A3Medium Mislabeled coverage: BR-MOVE-005 has no test at the validation seam

oracle/tests/game/battle.test.ts:206–219

The block describe('BR-MOVE-005 — stack size landing restriction') asserts error.rule === 'BR-MOVE-003'. The movement engine filters oversized targets before validateMove ever sees them, so the validator attributes the failure to reachability. The suite appears to cover BR-MOVE-005 at this seam but does not — and TEST.md Leg 1 requires every BR-xref to have a matching test identifier. Either rename the block to reflect what it proves, or declare the movement module the BR-MOVE-005 seam and drop the misleading describe.

A4Medium Assertions coupled to check ordering, not just behavior

oracle/tests/game/battle.test.ts:312–319 (pattern repeats across both files)

“rejects arata of Marshal (BR-ARATA-002 fires first — not in hand)” explicitly documents that the assertion depends on which check runs first. The business rules define no error precedence — any rejection of arata-ing a Marshal is correct. Reorder two legitimate checks and behavior stays correct while tests break. Asserting the error.rule vocabulary itself is legitimate (the error domain is part of the oracle contract); asserting precedence between two valid rejections tests the implementation, not the rules.

A5Medium Behavioral coverage gaps at the new seam

  • No negative Self-Check test for Arata — Marshal already in check, Arata that does not resolve it must be rejected. PROBE-4 confirms the code handles it correctly; only the test is missing.
  • No test for a Move that fails to resolve an existing check (PROBE-6 confirms the code handles it). The existing Self-Check test only covers post-move exposure.
  • No BR-CAPTURE-003 test through validateMove with an enemy target (source < target → illegal). The only size-restriction test uses a friendly target and asserts BR-MOVE-003.
  • Arata zone tested only for White — deploy zone received Black-symmetry tests (5 cases); the Arata zone logic is a separate implementation and received none.

A6Low Duplicated / weak assertions

battle.test.ts:215 “accepts move to empty square (trivially passes)” duplicates the same fixture+action asserted twice earlier (lines 143, 151). A few other “accepts” cases repeat identical inputs under different describes. Harmless, but inflates the count without adding signal.

A7Info Turncoat rejection tests cite a rule the action doesn’t violate

Guard tests assert non-empty turncoat is rejected with rule BR-STACK-006. The action may be perfectly legal per BR-STACK-006 — it is merely unimplemented. Citing a rule as violated when it isn’t misinforms consumers of the error domain. Prefer a dedicated marker (e.g. kind: 'unimplemented') or an honest rule value.

Axis 2 — Type quality: do the types serve a naive, absolutely explicit, easy-to-test oracle?

The core result types are good: discriminated unions make failure-with-payload unrepresentable, and the createStack() hardening already caught a real bug. The main weaknesses are a misleading afterState, a stringly-typed rule vocabulary, and duplicated result-type definitions.

B1High PlayValidation.afterState is typed as a real next state — but isn’t one

oracle/src/game/validation.ts:37–39, oracle/src/game/apply.ts:69–79, oracle/src/game/battle.ts:374–379

Step-8 applyMove does not flip the active player, increment the counter, or record history — it is a speculative artifact for Self-Check evaluation. Yet afterState: GameState is indistinguishable at the type level from a committed next state, and validatePlay’s JSDoc tells the future Game.applyAction it “can use [it] directly.” A consumer cannot tell that turn management is missing; the type lies by omission (and A2 cements it in tests).

Fix: brand it (e.g. { speculative: GameState } or a nominal SpeculativeState), state the gap in the type’s JSDoc, or stop exposing it until Step 10.

B2Medium GameError.rule is string

oracle/src/errors.ts:11

The error domain is the oracle’s contract, but any string compiles. A closed literal union ('BR-MOVE-001' | … | 'S1' | 'V3' | 'C1') would make the vocabulary explicit, typo-proof, and would let tests assert against a typed set — directly serving the “absolutely explicit” goal. The mis-citations found in C4/A7 are exactly what this would surface.

B3Medium Near-dead discriminator; fully dead error subclass

oracle/src/errors.ts, oracle/src/game/*

GameErrorKind is only ever set to 'self-check' (twice); everything else defaults to 'general'. IllegalActionError is never thrown anywhere in Step 8. Dead type surface misleads consumers about the shape of the error domain — populate it or remove it.

B4Medium Three ValidationResult definitions coexist

oracle/src/game/validation.ts:23 · oracle/src/gan/validate.ts:23 · oracle/src/gsfen/validate.ts:22

Step 8 created the shared module precisely to have “a single canonical definition instead of duplicates” (its own header), but the two older local definitions were not migrated. The unification is half-done.

B5Low Validators re-check kind at runtime; the Extract variants go unused

oracle/src/game/battle.ts:153–159, 266–272 vs oracle/src/game/apply.ts:24–27

validatePlay already dispatches on action.kind, making the per-validator kind checks redundant for internal flow. Meanwhile apply.ts defines MoveAction/ArataAction via Extract — but the validators don’t use them in their signatures. Either type the validators with the variants (compile-time safety) or keep the runtime checks as a deliberate public-API defense; the current mix gets neither benefit cleanly.

B6Low Cast-policy inconsistency in getArataZone

oracle/src/game/battle.ts:100, 119

Two inline (r + 1) as BoardCoord casts. The codebase’s stated policy confines as BoardCoord casts to audited helpers (squareFromIndex exists for exactly this). Minor, but the policy exists so reviewers can audit every cast in one place.

Axis 3 — Naivety: does the code hide or suppose logic beyond the business rules?

Most checks map one-to-one to BR-xxx references, in rule order, with citations — the naive ideal. The violations are structural: one invented rule, a duplicated (and divergent) validation stack, and rule semantics implemented twice in different modules.

C1High Invented rule: “Marshal must be placed on an empty square”

oracle/src/game/deploy.ts:143–149 (duplicated at oracle/src/gan/validate.ts:173–183)

validatePlacement rejects placing the Marshal on top of a friendly stack. No business rule supports this: BR-DEPLOY-005 allows placing a piece on one’s own pieces subject only to the size limit and the “never on top of a Marshal” restriction; GAN.md S2 requires the target to be “empty or a friendly non-Marshal-topped stack under size 3” — it constrains the top of the target, not the placed piece. BR-STACK-004 explicitly contemplates the Marshal belonging to a stack (“always the topmost Piece in any Stack it belongs to”), and the Step-7 saved test case uses stack [A,A,m].

PROBE-5 confirms the rejection fires. This is precisely the failure mode the review asked about: logic supposed beyond the business rules. Either a BR is missing (spec gap — record it) or the check must be removed. This needs a human decision; the code and the spec cannot both be right.

C2High Two public validation stacks exist — and provably diverge

oracle/src/gan/validate.ts (Step 4, S1–S6) vs oracle/src/game/deploy.ts + battle.ts (Step 8)

ORACLE.md planned Step 8 to wire the GAN-level S3/S4 stubs to the engine (“S3: Move legality — calls movement/attack modules”). Instead, parallel validators were built in game/ and the stubs remain live in the public API. Empirical divergences:

  • validateAction (S2) accepts stacking a piece onto a friendly Marshal; validatePlacement rejects it (BR-STACK-004). GAN.md S2’s “non-Marshal-topped” requirement is missing from the Step-4 implementation — so the older validator is non-conformant with its own spec (PROBE-2).
  • validateAction accepts any illegal move or arata — S3/S4 are stubs returning ok (PROBE-3).
  • Rule namespaces differ ('S2' vs 'BR-DEPLOY-004') for the same violation.

A naive oracle needs one validation path per action. Recommended: make gan/validate.ts delegate S2→validatePlacement, S3→validateMove, S4→validateArata (keeping the S-codes as aliases if the GAN contract needs them), or formally deprecate validateAction.

C3Medium Outcome semantics implemented twice

oracle/src/board/movement.ts:68–75 (determineOutcome) vs oracle/src/game/battle.ts:26–73 (validateOutcome)

The movement engine already computes forced/choice/null outcome for every destination (LegalMove.outcome); validateMove finds the matching LegalMove and then ignores that field, re-deriving the same logic — including the derived rule “Marshal on top ⇒ capture forced” (itself an inference from BR-STACK-002 condition 3, cited as BR-CAPTURE-002). Two sources of truth for BR-STACK-002/BR-CAPTURE-002: they agree today, drift would be silent. Also, movement.ts’s doc comment claims the validator rejects “friendly Marshal” targets — it rejects enemy-Marshal landings too (battle.test.ts:250 proves it); the doc has drifted from the code.

C4Medium Dead check with a mis-cited rule in validateArata

oracle/src/game/battle.ts:293–300

The piece === 'M' rejection is unreachable in legal play (the battle-phase Marshal is never in hand per BR-DEPLOY-011, and the hand check fires first regardless) — and it cites BR-ARATA-007, which governs placing onto a Marshal, not arata-ing the Marshal piece. The correct citation is GAN S4 (“is never M”) / BR-DEPLOY-011. Defensive checks are acceptable in an oracle, but they must be cited honestly and marked defensive; a wrong BR reference in the error domain is a spec-level bug, not a nit.

C5Medium validateMove JSDoc lists checks it does not perform

oracle/src/game/battle.ts:136–152

The header lists “2. BR-MOVE-001” and “4. BR-MOVE-005” as steps, both “implied by getLegalDestinations.” For an oracle whose stated principle is a one-to-one BR-to-code mapping, the doc should distinguish enforced here from enforced upstream at seam X — otherwise a coverage audit (or A3-style test) is misled into believing the validator owns those rules.

C6Low Marshal-first inferred from hand contents — two strategies for one rule

oracle/src/game/deploy.ts:91–99 vs oracle/src/gsfen/validate.ts (V3)

hand.M === 1 stands in for “Marshal not yet placed” — sound (initial count 1; only placement removes it) but indirect, and GSFEN V3 implements the same rule by scanning the board instead. Two inference strategies for one rule. The naive-explicit reading checks the direct fact (is my Marshal on the board?); better still, share one helper.

C7Low Noise in apply.ts

oracle/src/game/apply.ts:34–45

{ ...state.turn, done: state.turn.done } re-copies a field the spread already copies; ([...cell] as const) as typeof cell is a double cast fighting the tuple type. Not hidden logic — just noise a deliberately naive codebase shouldn’t carry.

C8Info Documented invention: Arata zone with no board pieces

oracle/src/game/battle.ts:85–89

The collapse-to-own-edge behavior when a player has no pieces on the board is invented (BR-ARATA-003 is silent) but documented and unreachable in legal play. Acceptable — and a good candidate for a one-line BR clarification so the spec owns it.

C9Info Explicitly-temporary functions made public API

oracle/src/index.ts (new exports) + oracle/src/game/apply.ts:8–12

applyMove/applyArata are documented as Step-8-only scaffolding (“Step 10 replaces them”) yet are exported from the public barrel, alongside afterState (B1). Consumers can now depend on a throwaway seam. Export from an internal path or mark @internal until Step 10 lands.

What Step 8 got right

  • Green and type-clean: 727/727 tests, tsc --noEmit clean, via the Docker toolchain as specified.
  • The saved Step-7 edge case is an excellent behavior test (SELF_CHECK_POS): it verifies Self-Check on the post-move state including stack-size change after capture — a test that catches a real bug class, not a mirror of the code.
  • Outcome-canonicity tests match GAN.md A1/S3 exactly, including both forced-capture directions and the documented invalid examples.
  • Result types are well-formed: ValidationResult/PlayValidation discriminated unions; exhaustive never checks in validatePlay; TurncoatLevels encodes GAN A3 at the type level.
  • BR citations on every error path, with checks ordered to match the rule documents — the naive-oracle ideal, mostly upheld.
  • The type hardening proved itself: createStack() runtime validation caught the forced-capture (outcome=null) bug during the step — evidence the explicit-types strategy pays off.
  • Honest commit message: states what was built, what was deferred, and the bug caught.
